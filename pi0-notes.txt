Perplexity implementation of operator*=
void operator*=(const dynsiz& b) {
    dynsiz prod(ds.size() + b.ds.size());

    for (size_t i = 0; i < ds.size(); ++i) {
        uint16_t carry = 0;
        for (size_t j = 0; j < b.ds.size(); ++j) {
            uint32_t cur = prod.ds[i + j] + ds[i] * b.ds[j] + carry;
            prod.ds[i + j] = cur & 0xff;
            carry = cur >> 8;
        }
        prod.ds[i + b.ds.size()] += carry;
    }

    ds = std::move(prod.ds);
}
That version:

    puts each partial product in the correct position,

    handles carry locally,

    avoids diagonal bookkeeping mistakes,

    avoids depending on operator+= during multiplication.

Also worth fixing

A few other issues can cause “sometimes wrong” behavior:

    operator+=(dynsiz b) and operator-=(dynsiz b) take arguments by value, which is wasteful and can hide bugs.

    operator<<= has a suspicious carry-out line:

    cpp
    ds[ds.size()-1] = (bsds[ds.size()-2]>>wordbits);

    That looks like it may write the wrong carry source.

    ensureEqLen(&b) mutates the copy of b, which is okay here, but the design is unusual and easy to misuse.

    You are using word (uint8_t) for intermediate subtraction/addition in pm(). That can work, but it is easy to overflow silently if not handled very carefully.

The core problem in operator*= is the wrong placement of partial products, not the multiplication itself.
